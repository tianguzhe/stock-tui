## 🔧 加仓闸门缺口评估（**方案待定，代码未改**，08-29 提出）

**缺口性质：不是 bug，是设计边界。** `screener.AddOnBlocked` 的前置条件是「浮亏 ＋ SAR/ST 双空」，专治**浮亏摊平**（依据 06~08 审计：22 次加仓中 15 次为摊平，均值 −9.5%）。亨通 08-28 那笔是**另一类问题**：浮盈 +18%、双多、score 59 —— 三个前置条件一个不沾。

| 加仓类型 | 现有闸门 | 亨通 08-28 |
|---|---|---|
| 浮亏 + 趋势破位（摊平）| 🟢 已覆盖（score 路径 ＋ 深亏兜底）| — |
| **浮盈 + 趋势完好 + 敞口爆表** | 🔴 **零覆盖** | ✅ 正是这一类 |

**方案：新增一条与现有路径完全正交的敞口闸门。** 数据全部现成，无需加列、无需改 snapshot：

```go
// 复用 effectiveStop + RiskPerTrade，与 PositionHint 同一口径
exposure := (c.Close - stop) * float64(h.Shares)
multiple := exposure / (capital * RiskPerTrade)
if multiple > AddOnMaxExposure { /* 禁止加仓 */ }
```

**⚠️ 落地前必须先解决的两件事（未变）**：

1. 🔴 **贴身止损会让敞口失真到接近零** —— 兴业 `effectiveStop` 取 low20 **17.42**（距现价 0.68%），敞口算出来只有 **48.00 元（0.06×）**，**看起来是全组合最安全的仓位**，而它三天前刚被击穿。`PositionHint` 有 `MinStopPct`=2% 拦这种情况，**敞口计算没有** —— 直接上敞口闸门会造出「止损越贴身、越允许加仓」的反向激励。**这是本方案最大的风险点，须先补齐同款保护。**
2. 🟡 **阈值需回放 06~08 审计窗口定标**。现有闸门当初是「拦 7 笔、零误伤」才定的 50/20% 双阈值，敞口闸门应走同一流程。

🆕 **今日新增的一条设计约束**：**敞口闸门的阈值必须与「档位退化」共存。** 今日三只标的在**仓位完全没变**的情况下敞口跳升（华天 +46%），若阈值定得紧（如 1.0×），会出现「昨天允许加仓、今天禁止加仓，而中间什么操作都没做」的抖动。**建议阈值取 2.0× 并配合 ÷ATR ≥1.3 的档位过滤，避免闸门被档位噪音驱动。**
